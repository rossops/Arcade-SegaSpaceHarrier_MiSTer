# Space Harrier i8751 (315-5163A) — what the MCU actually does

This is a full read of the dumped Space Harrier protection MCU, an Intel 8751
with 4 KB of internal mask ROM. The dump is `315-5163a.ic32` from MAME 0.289's
`sharrier` set, SHA1 `73801db79756b0ffdd54b298814e3eeb088fe8c2`, which matches
the `ROM_LOAD` in `segahang.cpp`. The full disassembly sits next to this file as
`i8751_315-5163a.lst`; every address I cite below is a line in there. I wrote a
small table-driven MCS-51 disassembler for it (`scratchpad/dis51.py`) because
capstone has no 8051 backend.

Everything here is read off the bytes. Where the code is ambiguous or I couldn't
pin something down, I say so instead of guessing.

## How the MCU reaches the main bus (the decode you have to implement)

The MCU's external DATA space is a window onto the main 68000 bus. Two things
set the address:

- **Port 1 picks the 64 KB window and drives the IPL.** MAME's `i8751_p1_w`:
  `m_i8751_addr = (BIT(data,6) << 4) | ((data & 0x38) >> 3)`, then the byte
  address is `(m_i8751_addr << 16) | (offset ^ 1)`. Unpacked, the window bits
  map to main-bus address lines like this:

  | P1 bit | role        |
  |--------|-------------|
  | 7      | halt? (this MCU never uses it) |
  | 6      | A20         |
  | 5      | A18         |
  | 4      | A17         |
  | 3      | A16         |
  | 2:0    | 68000 IPL, **inverted** (`~P1 & 7`), HOLD_LINE per write |

  Note A19 is always 0 — the window bit that would drive it (`m_i8751_addr`
  bit 3) is never populated. So the reachable windows are a sparse set, listed
  below.

- **DPTR (or `P2:Ri`) is the offset, XOR 1.** `movx @dptr` uses the full 16-bit
  DPTR; `movx @Ri` uses `(P2 << 8) | Ri` (MAME `i8051.cpp` `external_ram_iaddr`).
  The `^1` swaps the byte lane, so DPTR `0x0384` reaches main-bus byte `0x0385`.

Concrete window table, computed from every distinct P1 value the code writes:

| P1 written | window base | how it shows up |
|------------|-------------|-----------------|
| `0xFF` | `0x170000` | idle / park value, IPL 0 |
| `0xEF` | `0x150000` | INT0 handler write, IPL 0 |
| `0xEB` | `0x150000` | same window mid-INT0, **IPL 4** |
| `0xA7` | `0x040000` | main 68000 work RAM (the big one) |
| `0xAF` | `0x050000` | reset only |
| `0xB7` | `0x060000` | timer-0 handler |
| `0xC7` | `0x100000` | reset (`0x0DEF`) |
| `0xCF` | `0x110000` | reset block write |
| `0xD7` | `0x120000` | per-frame writes |
| `0xE7` | `0x140000` | per-frame writes |
| `0x87/0x8F/0x97/0x9F` | `0x000000/010000/020000/030000` | ROM checksum |

There's one subroutine, `L0568`, that changes only the window and preserves the
low bits: `mov a,P1 / anl a,#0x87 / orl a,r7 / mov P1,a`. The mask `0x87` keeps
P1.7 and P1[2:0], so a window change through `L0568` never disturbs the IPL. The
caller passes the window nibble in `r7` (`0x20`→win `0x04`, `0x50`→win `0x12`,
`0x60`→win `0x14`, `0x00`→win `0x00`).

## The contract an RTL bridge has to honor

**Address decode.** Implement exactly the map above: window from `{P1.6, P1.5,
P1.4, P1.3}` placed at `{A20, A18, A17, A16}` with A19 forced 0, offset from the
16-bit DPTR (or `P2:Ri` for `movx @Ri`) XORed with 1. Nothing exotic; MAME's two
lines are the whole spec.

**Which regions the MCU actually touches.**

- **Reads main ROM `0x000000–0x03FFFF`.** Once, at boot, in the checksum loop
  `L09AB`. It walks all four 64 KB ROM banks (windows 0–3) and folds them into a
  32-bit accumulator, then compares against the constants `0xF1B4` / `0x7ED0`
  baked in at `0x01FF`/`0x0205`. So the bridge must give the MCU real read access
  to the maincpu ROM, not just RAM. A wrong or missing ROM read here doesn't hang
  the MCU — it just sets an internal "bad" flag (see below) — but the game won't
  behave.
- **Reads and writes main work RAM `0x040000–0x043FFF`** constantly (window
  `0x04`). This is where the interesting handshake lives.
- **Writes windows `0x10`, `0x11`, `0x12`, `0x14`** with block/parameter writes
  each frame (`0x100000`, `0x110000`, `0x120000`, `0x140000`). These are the
  MCU pushing precomputed tables to the main CPU's peripheral/RAM space; a bridge
  that only wired up work RAM would drop them.
- **Reads/writes windows `0x15` and `0x17`** that go nowhere on the real board
  and that MAME ignores — the "150000 write" and the "170000 read". Details
  below. A bridge can safely let these fall on the floor (unmapped read returns
  don't-care, writes discarded), which is what the hardware does.

**IPL behavior.** The MCU is the main 68000's *only* interrupt source on
`sharrier` — MAME removes the CPU's own vblank IRQ. The MCU raises exactly one
level, **IRQ 4**, exactly once per vblank, and only from inside the INT0 handler.
It does it by toggling P1.2: the window byte is `0xEF` (IPL 0), it does
`clr P1.2` → `0xEB` (`~0xEB & 7 = 4`, IRQ 4 asserted), waits out a short delay
loop, then `setb P1.2` → `0xEF` (IPL back to 0). MAME asserts on HOLD_LINE, so
the level stays latched into the 68000 until it's acknowledged; the MCU's `setb`
just stops driving it. No other P1 value in the whole image has a non-`111` low
nibble, so **IRQ 4 per frame is the complete IPL story** — there is no IRQ 1/2/3
path, no per-command interrupt, nothing else. The bridge needs: on the P1 write
that clears bit 2, latch a level-4 IRQ to the main CPU (autovectored), and let
it clear on the main CPU's IACK, not on the MCU's `setb P1.2`.

One caveat: the INT0 handler skips the whole write-and-pulse block if internal
bit `0x21.0` is set, and that bit is set at boot when the ROM checksum fails. So
"no IRQ 4 reaching the main CPU" is a legitimate symptom of the MCU deciding the
main ROM is bad. If you stub the MCU's ROM reads, make them pass the checksum or
the MCU will silently stop interrupting the 68000.

**Timing tolerance.** The MCU paces its bus accesses with a fixed delay sub
`L0570` (`mov a,#4 / djnz` — a handful of machine cycles) between the address
setup and the data phase, and it reads every external location *twice* before
using it (e.g. `L0789`, `L07D9`, `L089A`). That double-read with a delay between
is the MCU giving the shared bus time to settle. Practical implication for the
bridge: the MCU tolerates arbitration latency fine — it isn't cycle-counting the
68000 — but you must make sure the *second* read returns the settled value, and
that a read and its paired write in a read-modify-write (`L07D9`, `L08AD` region)
see a coherent RAM. There are no tight busy-wait handshake loops against external
addresses anywhere: the two loops that look like polling in reset (`L0195` on
DPTR `0xD500`, `L01B4` on DPTR `0xCBEB`) are pure `inc dptr` delay loops, no
`movx` in them. So the MCU never spins waiting for the 68000 to answer.

**The 40385 write MAME suppresses — you probably should not special-case it.**
See the dedicated section; the short version is that the only writes the MCU ever
makes to `0x40385` are two zeroing writes during its own reset, and MAME's blanket
suppress is papering over a reset-ordering race, not an ongoing protocol.

## Reset / init sequence (`L0123`)

Straight-line setup:

```
0123  mov IE,   #0x03     ; enable EX0 (INT0) + ET0 (timer0). INT1/T1/serial off
0126  mov IP,   #0x00     ; no priority
0129  mov TCON, #0x05     ; IT0=1, IT1=1 (both ext ints edge-triggered), timers stopped
012C  mov TMOD, #0x11     ; T0 and T1 both mode 1 (16-bit)
012F  mov TH0/TL0 = 0
0135  mov PSW,  #0x00     ; register bank 0
0138  mov SP,   #0x50
013B  mov P1,   #0xFF     ; window 0x17, IPL 0  (park)
013E  mov P3,   #0xFF
0143  clear internal RAM 0x00..0x7F
```

So at boot P1 = `0xFF`: window `0x170000`, **IPL driven = 0** (all three low bits
high → `~0xFF & 7 = 0`). The MCU does not assert any interrupt at reset.

Then, in order:

1. **Internal-ROM self-check** (`L0155`): sum its own 4 KB via `movc`, compare
   against the 16-bit value stored at `0x0EF0`. Mismatch → `L0187`, an infinite
   `mov P1,#0xFF / sjmp` park (dead MCU, IPL 0 forever).
2. A block write of a 0x2D-byte table (from `0x0BDF`) to window `0x11`
   (`0x110000`), via `L0BCD`. P1 = `0xCF` at this point.
3. **Clears 0x40385 to zero, twice** (`L01A2`): `mov P1,#0xA7` (window `0x04`),
   `mov dptr,#0x0384`, `clr a`, `movx @dptr,a` … `movx @dptr,a`. Byte address
   `0x040000 | (0x0384 ^ 1) = 0x040385`. **These two writes are exactly what
   MAME's `i8751_w` throws away.**
4. **Main-ROM checksum** (`L09AB` called four times with `B` = `0x87/0x8F/0x97/
   0x9F`, i.e. windows 0–3). Result in `r2:r3:r4:r5`, compared against
   `0xF1B4` / `0x7ED0`. On mismatch it sets internal flags `0x20.0` and `0x21.0`;
   on match it leaves them clear. `0x21.0` is later read by the INT0 handler to
   decide whether to interrupt the 68000 at all.
5. Housekeeping: `anl TCON,#0x55` (clear the overflow/edge flags, keep run bits),
   seed counters `0x34=0xC0`, `0x30=0x0A`, `0x31=0x1E`, then `setb EA` (`0x22C`)
   — global interrupts on. From here the MCU runs its main loop.

## Main loop (`L0234`, once per vblank)

The loop body runs, then blocks at `L025B` `jb INT0, L025B` until the INT0 line
goes low again — i.e. it runs exactly once per vblank pulse. Each pass:

- `L0ABC` — an RNG/scratch churn seeded from internal `0x35` (`mul`, then a
  `movx` read loop). **Crucially, P1 is still parked at `0xFF` here**, so those
  `movx a,@dptr` reads land in window `0x17` = `0x170000–0x17FFFF`. This is the
  "reads 170000 (by accident?)" MAME notes: it's a seed-churn reading garbage
  from the idle window, not a deliberate access. The values are only used to
  perturb `0x35`.
- `L089A` — per-frame data build. If internal `0x22.0` is set it does one path
  (window `0x04`, `0x040492`); otherwise it loops over counter `0x32` reading
  window `0x14` (`0x140020`/`0x140030`) and writing window `0x04`
  (`0x040490`-ish).
- `L0678` — increments the 16-bit internal counter `0x33:0x34`; when it wraps to
  zero it emits a burst of writes to windows `0x04`/`0x12`/`0x14` and toggles
  timer 0 (`setb TR0`).
- `jb 0x22.0, +` then `L0789` — the 40385 watcher, only while `0x22.0` is clear.
- `L0AD6` — a block write (via `L0BCD`) to window `0x12` at `0x1244F5`, length
  chosen from bit `0x33.2`.
- `mov P1,#0xFF` (re-park), `setb EA`, wait for next vblank.

## INT0 / vblank handler (`L0345`)

This is the whole vblank interaction with the main CPU. It gets INT0 from the
screen's vblank at 60 Hz.

```
0345  push ACC/PSW/DPL/DPH/P1
034F  clr RS1 / setb RS0        ; register bank 1
0353  clr IE0                   ; ack the edge
0355  jb 0x21.0, L0368          ; ROM checksum was bad -> skip everything, just reti
0358  mov P1,#0xEF              ; window 0x15
035B  mov a,#0x1C
035D  movx @r0,a               ; write 0x1C.  offset = P2:r0 = 0xFF00 (P2 never set,
                                ;   bank1 r0 cleared at reset), ^1 -> 0xFF01,
                                ;   so main-bus 0x15FF01.  MAME rounds this to
                                ;   "150000"; the whole 0x15 window is unmapped
                                ;   on sharrier and MAME ignores the write.
035E  lcall L0570              ; settle delay
0361  clr P1.2                 ; P1 0xEF -> 0xEB : ASSERT IRQ 4 to main 68000
0363  lcall L0570              ; hold it a few cycles
0366  setb P1.2               ; P1 0xEB -> 0xEF : stop driving IPL
0368  pop P1/DPH/DPL/PSW/ACC
0372  reti
```

So per vblank, on a good board: one ignored write to the `0x15` window, then a
single IRQ-4 pulse to the main CPU. That pulse is the main 68000's only vblank
interrupt. The handler touches **no work-RAM address** — it does not read or
clear `0x40385`, does not read inputs. It is purely "tell the 68000 a frame
happened." If `0x21.0` is set (bad main ROM) it does nothing at all, so the main
CPU never gets its vblank IRQ.

Note the write target is `0x15FF01`, not a clean `0x150000` — that comes from
`P2` sitting at its `0xFF` reset default (the code never writes P2) and bank-1
`r0` being 0. MAME's comment rounds it off because the whole window is ignored
anyway. I'm flagging the exact value in case the bridge maps part of window `0x15`
to something real; it shouldn't, but if it does, expect the write at `0x15FF01`.

## The 40385 interaction — the actual protocol

This is the important one, and the reality is narrower than MAME's comment
suggests.

**Where 40385 is written by the MCU:** only at reset, `L01A2`, two zeroing
writes (step 3 above). Nowhere else in the entire 4 KB. I checked every
`mov dptr,#0x0384` and there are exactly two: the reset write (`0x01A2`) and the
main-loop read (`0x078D`). There is no `movx @Ri` that can reach `0x040385`
either (those use `P2:Ri` and P2 stays `0xFF`, so they land in window `0x04` only
if the code sets P2 to `0x04`-producing... it never touches P2).

**Where 40385 is read by the MCU:** in `L0789`, the main-loop watcher, once per
frame while internal bit `0x22.0` is clear:

```
0789  mov r7,#0x20 / lcall L0568   ; window -> 0x04
078D  mov dptr,#0x0384
0790  movx a,@dptr                 ; read 0x040385
0791  lcall L0570                  ; settle
0793  movx a,@dptr                 ; read 0x040385 again
0794  lcall L0570
0796  jz L07D0                     ; if 0x40385 == 0 -> "idle" branch
      ; nonzero branch: run the RMW magic checks (below)
```

Idle branch (`L07D0`): decrement internal counter `0x31`; if it hits 0, `setb
0x22.0`. Once `0x22.0` is set the main loop stops calling `L0789` at all (guard
at `0x024D`) and `L089A` switches to its alternate path. So `0x40385` staying
zero for `0x1E` (30) consecutive frames flips the MCU into a different mode.

Nonzero branch: `L07D9` is called on a short list of work-RAM bytes, each with a
different additive constant, checking whether `byte + const == 0`:

| DPTR | main-bus addr | constant | passes when byte == |
|------|---------------|----------|---------------------|
| `0x0381` | `0x040380` | `0xB7` | `0x49` |
| `0x04F4` | `0x0404F5` | `0xBF` | `0x41` |
| `0x02F4` | `0x0402F5` | `0xAE` | `0x52` |
| `0x43E2` | `0x1243E3` (window `0x12`) | `0xBF` | `0x41` |

`L07D9` reads the byte (twice, with delays), adds the constant, **writes the sum
back**, and returns with Z set if the sum was zero. If any of the first three
match (Z), it jumps to `L07C4` and reloads the counters `0x30=0x0A`, `0x31=0x1E`.
The values `0x49 0x41 0x52 … 0x41` ('I','A','R'…'A') look like a signature the
main program is expected to have deposited — this is Sega's usual "MCU pokes and
checks magic bytes in shared RAM" protection, not a clean command register.

**So what is `0x40385`, really?** It's a **liveness / heartbeat flag the main
68000 sets and the MCU polls** — a watchdog-style handshake, not a command byte
the MCU consumes and clears. The main program writes something nonzero to
`0x40385` while it's running normally; the MCU, each frame, reads it: nonzero =
"main CPU alive, run the protection checks and keep the counters topped up",
zero for 30 frames = "main CPU stalled, flip mode via `0x22.0`". The MCU **does
not clear `0x40385`** in steady state. The only clears are the two at reset,
before the main CPU has written anything meaningful there.

**Why MAME suppresses the write, and what the bridge should do.** MAME's
`i8751_w` drops any write to `0x40385` with the note that "the mcu clears this
value after the cpu sets it." Given the code, the sole MCU writes to `0x40385`
are the two reset zeros at `L01A2`. In a faithful implementation these fire while
the MCU is still in its own reset init, *before* the main 68000 has reached the
point where it writes its heartbeat. On the real board the relative boot timing
guarantees the MCU's clears land first and are harmless. MAME's CPU scheduling
can interleave them the other way — main CPU writes its heartbeat, then the MCU's
still-pending reset clear wipes it — and the game wedges. The blanket suppress is
a sledgehammer fix for that one reset race.

For our RTL bridge: **do not special-case `0x40385`.** Treat it as ordinary work
RAM, writable by the MCU like any other byte. Get the reset ordering right
instead — the MCU finishes its init (through `L01A2`) before the main 68000
executes its heartbeat write, which is the natural outcome if both come out of
reset together and the MCU's short init runs to completion first. If we ever see
the same wedge MAME saw (heartbeat at `0x40385` getting stomped to 0), that's the
tell that our reset timing has the two clears landing late, and the fix is timing,
not a hardcoded address filter. Worth building the board bench with a tap that
logs any write of 0 to `0x040385` after the first main-CPU heartbeat, so we catch
the race if it happens rather than papering over it.

## Interrupt/timer setup summary

- `IE = 0x03`: only INT0 (EX0) and timer 0 (ET0) enabled. INT1, T1, and serial
  are masked the whole time. The INT1 (`L0456`) and T1 (`L0567`) vectors are bare
  `reti`; the serial vector (`0x0023`) is `reti` too.
- INT0 is the vblank line, edge-triggered (`IT0=1`), 60 Hz — the per-frame engine.
- Timer 0 (`L0457`) is a 16-bit mode-1 timer, started (`setb TR0`) inside `L0678`.
  Its handler drives a small state machine off internal bytes `0x35/0x36/0x37`
  and, when a DPTR counter wraps, writes one byte to window `0x06` (`0x060000`)
  via `mov P1,#0xB7`. It never touches `0x40385` or the IPL bits. It looks like a
  slow secondary output channel; I didn't fully reverse its cadence and I'm not
  going to pretend I did.

## Loose ends I couldn't fully resolve

- The exact semantics of the window `0x10`–`0x14` block writes (what the main
  CPU expects at `0x100000`, `0x120000`, `0x140000`) aren't determinable from the
  MCU alone — they're just table pushes; you'd need the main-CPU side to know
  what they mean. For the bridge that's fine: it only has to deliver the bytes.
- The `0x1243E3` check in `L0789` is the one that reads through window `0x12`
  rather than work RAM; I've listed it but I can't tell you what's normally at
  `0x1243E3` on the main bus without tracing the 68000.
- The `0x15FF01` vs `0x150000` write target: resolved as far as the arithmetic
  goes (P2 default + bank-1 r0 = 0), but since the window is ignored it doesn't
  matter unless the bridge maps window `0x15`.
